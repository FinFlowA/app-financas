# PoCs seguros da auditoria FinFlow

Data: 15/08/2026

Este documento contém provas locais, estáticas ou somente leitura. Ele não contém segredos reais, payload destrutivo, malware, imagem malformada nem instrução para atacar serviços de terceiros.

## Regras de execução

- Use apenas este repositório, um Supabase local ou um projeto de homologação com dados fictícios.
- Não execute UPDATE, DELETE, replay, força bruta ou interceptação contra produção.
- Não copie access token, refresh token, chave de provedor ou PII para issue/log.
- Se um comando imprimir segredo acidentalmente, apague o terminal/log e rotacione a credencial.
- Testes que alteram dados devem usar fixtures descartáveis e terminar em rollback.

## PoC 1 — Prova negativa de segredos versionados

Na raiz:

~~~powershell
npm run security:check
git ls-files | rg '(^|/)(\.env|.*\.(pem|p12|pfx|key)|service-account|credentials|secrets?)'
git grep -n -I -E '(service_role|sb_secret_|gsk_|sk_live_|BEGIN (RSA |EC )?PRIVATE KEY)'
~~~

Resultado obtido nesta auditoria:

- security:check aprovado;
- somente .env.example e web/.env.local.example apareceram como arquivos de ambiente versionados;
- nenhum valor real de segredo foi confirmado.

Limitação: o verificador agora inclui web, mas os comandos acima inspecionam o estado atual, não todo o histórico. Em CI, completar com gitleaks/trufflehog no histórico.

Nunca cole no relatório a linha que contiver um possível segredo; registre apenas caminho, tipo e status de rotação.

## PoC 3 — Fluxo implícito com tokens em custom URL scheme

Prova estática:

~~~powershell
rg -n '"scheme"|emailRedirectTo|redirectTo' app.json app/login.tsx app/seguranca.tsx
rg -n 'flowType|createClient|access_token|refresh_token|setSession|exchangeCodeForSession' lib/supabase.ts app/_layout.tsx
~~~

Sinais esperados antes da correção:

- app.json registra meuappfinancas;
- redirects usam meuappfinancas://;
- createClient não define flowType: "pkce";
- _layout trata access_token e refresh_token vindos do fragmento.

Prova da dependência instalada, sem abrir nenhum link real:

~~~powershell
npm ls @supabase/supabase-js
Select-String node_modules/@supabase/supabase-js/src/lib/constants.ts -Pattern 'flowType'
~~~

Não gere URL com token real e não registre outro aplicativo para capturar o esquema. A evidência estática já comprova a superfície.

Teste negativo após a correção, com conta de laboratório:

1. Solicitar recuperação.
2. Confirmar que o link é HTTPS em domínio verificado.
3. Confirmar que contém code, não access_token/refresh_token.
4. Confirmar que o código só é trocado no dispositivo que iniciou PKCE.
5. Confirmar que um callback fictício com fragmento é ignorado.

## PoC 4 — delete_user não exige step-up no servidor

Prova no repositório:

~~~powershell
rg -n 'CREATE OR REPLACE FUNCTION delete_user|SECURITY DEFINER|DELETE FROM auth.users' docs/supabase-migration.sql
rg -n 'delete_user|grant execute' supabase/migrations/20260730_secure_subscriptions.sql
rg -n 'signInWithPassword|rpc\("delete_user"\)|LocalAuthentication' web/src/app app
~~~

Consulta somente leitura para confirmar a definição remota no SQL Editor:

~~~sql
select
  p.oid::regprocedure as function_name,
  p.prosecdef as security_definer,
  p.proconfig as function_config,
  has_function_privilege('authenticated', p.oid, 'EXECUTE') as authenticated_can_execute,
  pg_get_functiondef(p.oid) as definition
from pg_proc p
join pg_namespace n on n.oid = p.pronamespace
where n.nspname = 'public'
  and p.proname = 'delete_user';
~~~

Critério de vulnerabilidade:

- authenticated_can_execute = true;
- a definição usa apenas auth.uid() e não valida reautenticação recente/nonce/AAL.

Não chame a função como teste. Exclusão é irreversível e a inspeção do catálogo é suficiente.

## PoC 5 — Política permite alteração ampla de caixinhas

Prova estática:

~~~powershell
rg -n 'caixinhas_partner_update|preserve_finflow_row_identity|grant select, insert, update, delete' supabase/migrations/20260731000100_harden_core_rls.sql
rg -n 'saldo_atual|from\("caixinhas"\).*update|from\(''caixinhas''\).*update' 'app/(tabs)/caixinhas.tsx'
~~~

Consultas remotas somente leitura:

~~~sql
select
  schemaname,
  tablename,
  policyname,
  cmd,
  roles,
  qual,
  with_check
from pg_policies
where schemaname = 'public'
  and tablename = 'caixinhas'
order by policyname;
~~~

~~~sql
select
  grantee,
  privilege_type,
  column_name
from information_schema.column_privileges
where table_schema = 'public'
  and table_name = 'caixinhas'
  and grantee in ('authenticated', 'anon')
order by grantee, privilege_type, column_name;
~~~

Critério de vulnerabilidade: o parceiro passa pela policy de UPDATE, e não existe proteção de coluna/trigger impedindo saldo_atual de mudar fora de uma RPC financeira.

Teste funcional recomendado somente em Supabase local:

1. Criar usuários sintéticos A e B.
2. Formar parceria e objetivo compartilhado fictício com saldo zero.
3. Tentar alterar saldo_atual diretamente como B dentro de fixture descartável.
4. Verificar que o banco deve negar a operação.
5. Executar a RPC oficial e verificar transação + saldo no mesmo commit.
6. Descartar a base local.

Não inclua IDs reais, JWTs ou URL de produção no teste.

## PoC 6 — Fallback de sessão no AsyncStorage

~~~powershell
rg -n 'nativeSecureStore|AsyncStorage.getItem|AsyncStorage.setItem|expo-secure-store' lib/supabase.ts app.json
~~~

Critério de vulnerabilidade no APK legado:

- nativeSecureStore ausente;
- setItem usa AsyncStorage;
- o objeto persistido é a sessão do Supabase.

Critério de correção em novo binário:

- o módulo ExpoSecureStore está presente;
- a sessão é migrada ao Keychain/Keystore;
- o valor legado é removido;
- reinício e renovação da sessão continuam funcionando.

Não extraia token de aparelho de usuário. Faça a validação em dispositivo de laboratório com conta sintética.

## PoC 7 — Dependência image-size no pipeline

~~~powershell
npm ls image-size metro @expo/metro expo --all
Select-String package-lock.json -Pattern 'node_modules/image-size','node_modules/metro','"image-size":'
npm audit --json
~~~

Resultado observado:

- Metro 0.83.3 usa image-size ^1.0.2;
- lockfile resolve 1.2.1;
- npm audit --offline retornou zero por não ter os avisos no cache local;
- npm audit online reportou 10 nós de severidade alta, todos convergindo na cadeia Expo/Metro/image-size;
- os advisories oficiais marcam versões até 2.0.2 como afetadas.

Referências:

- https://github.com/advisories/GHSA-w3rx-r6r6-pgpr
- https://github.com/advisories/GHSA-5p2g-fcmc-qvqq

Não baixe nem gere imagens malformadas. A versão e o caminho de dependência bastam para demonstrar exposição do pipeline. Esse pacote está no Metro; não foi encontrado caminho de entrada de imagem remota no runtime instalado.

## PoC 8 — CSP permite script inline

Inspeção estática:

~~~powershell
rg -n 'Content-Security-Policy|script-src|unsafe-inline|unsafe-eval' web/next.config.ts
~~~

Inspeção local:

Terminal 1:

~~~powershell
Set-Location web
npm run dev
~~~

Terminal 2:

~~~powershell
curl.exe -I http://localhost:3100/login
~~~

Resultado esperado antes da correção: Content-Security-Policy contém script-src 'self' 'unsafe-inline'. unsafe-eval deve aparecer apenas em desenvolvimento.

Depois de adotar nonce/hash, executar os fluxos de login, cadastro, dashboard e service worker e confirmar que o navegador não registra violação inesperada.

## PoC 9 — Timestamp do webhook não possui janela de validade

~~~powershell
rg -n 'parts\.ts|manifest|Date\.now|clock|timestamp|eventId|payload\.id' supabase/functions/_shared/mercado-pago.ts supabase/functions/mercado-pago-webhook/index.ts
~~~

Resultado esperado antes da correção:

- parts.ts é obrigatório e participa do HMAC;
- não existe comparação entre ts e o horário atual;
- payload.id alimenta a deduplicação, embora não componha o manifesto assinado.

Teste unitário local recomendado, sempre com segredo falso:

- assinatura válida e timestamp atual → aceita;
- assinatura válida e timestamp antigo → deve rejeitar;
- mesmo evento repetido → deve retornar replayed sem nova consulta;
- evento com ID de payload alterado, mas mesmos dados assinados → deve continuar deduplicado.

Não faça replay no endpoint publicado.

## PoC 10 — Service worker não armazena dados financeiros

~~~powershell
Get-Content web/public/sw.js
~~~

Critérios positivos:

- fetch ignora método diferente de GET;
- exige mesma origem;
- somente /_next/static e STATIC_PATHS entram no cache;
- HTML autenticado e respostas Supabase não são armazenados.

No navegador local, após navegar pelo site:

~~~javascript
await caches.keys()
~~~

Em Application → Cache Storage, verificar que não existe resposta de /transacoes, /contas, Supabase REST ou HTML do dashboard. Não exporte o cache de uma sessão real.

## PoC 11 — GitHub Pages não suporta o site completo

~~~powershell
rg -n '"use server"|createServerClient|cookies\(\)|headers\(\)|NextResponse' web/src web/next.config.ts
Get-Content web/package.json
~~~

Critério:

- presença de Server Actions, proxy de sessão, route handler e cookies de servidor;
- ausência de output: "export" e de processo servidor no GitHub Pages.

Prova negativa: um export estático não consegue executar essas funções. Não tente “corrigir” removendo o proxy/cookies, pois isso reduziria a segurança. Use runtime Next compatível.

## Plano DAST seguro para uma etapa futura

Este plano não foi executado nesta auditoria:

1. Subir Supabase local e site/app apontando exclusivamente para ele.
2. Criar dois usuários fictícios e dados sem relação com produção.
3. Executar OWASP ZAP em modo passivo contra localhost.
4. Testar autorização trocando apenas IDs das fixtures e confirmar resposta 401/403/404.
5. Testar limites com volume baixo e controlado; parar no primeiro 429.
6. Rodar MobSF local contra APK de homologação sem credenciais reais.
7. Restaurar/destruir somente o ambiente descartável.

Não instalar certificado de interceptação em aparelho pessoal com aplicativos bancários. Não interceptar tráfego de terceiros. Não desabilitar TLS, RLS ou assinatura para “facilitar” o teste.

## Evidência mínima para fechar cada achado

Para cada correção, anexar:

- commit;
- teste que falhava antes e passa depois;
- saída sanitizada da verificação;
- ambiente e versão do binário;
- confirmação de implantação;
- rollback documentado.

Nunca anexar JWT, cookie, número de telefone, e-mail real, saldo, chave ou conteúdo financeiro.

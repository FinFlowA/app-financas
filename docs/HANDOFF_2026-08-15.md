## 2. Site novo em Next.js (`/web`)

Painel web separado do app mobile, mesma base do Supabase (mesmos usuários,
contas, RLS). Rodando localmente em `localhost:3100`.

### Stack e decisões técnicas

- **Next.js 16** (App Router, Turbopack) + **React 19** + **TypeScript**.
  Atenção: esta versão renomeou Middleware para **Proxy** (`src/proxy.ts`,
  não `middleware.ts`) e `cookies()`/params de rota são assíncronos — ver
  `web/AGENTS.md` antes de mexer no roteamento.
- **Tailwind CSS v4** (config via `@theme` em `globals.css`), com os mesmos
  tokens de cor do app mobile (`constants/finflow-design.ts` portado).
- **@supabase/ssr** para autenticação (cookies HttpOnly, sessão renovada a
  cada navegação pelo proxy).
- Sem biblioteca de gráficos — os dois gráficos de Relatórios são SVG
  desenhados à mão, seguindo o skill interno de visualização de dados do
  workspace (paleta, marcas, tooltip acessível, etc.).

### Funcionalidades prontas

| Rota | O que faz |
|---|---|
| `/login` | Autenticação com e-mail/senha (mesma conta do app) |
| `/` (Início) | Saldo geral, entradas/saídas do mês, cartões de conta na cor escolhida pelo usuário |
| `/transacoes` (Histórico) | Lista de lançamentos com conta e categoria coloridas |
| `/objetivos` | Lista com barra de progresso · criar objetivo · **Guardar/Resgatar** dinheiro |
| `/cartoes` | Lista de cartões com limite usado/disponível · criar cartão |
| `/cartoes/[id]` | Fatura do mês atual, adicionar compra, **pagar fatura**, histórico de faturas anteriores |
| `/relatorios` | Um gráfico único (barras de receita/despesa + linha de saldo acumulado **com projeção baseada em lançamentos pendentes**, mesmo eixo, mesmo ponto de 0) · despesas por categoria do mês |

### Sobre as operações que mexem em dinheiro (Guardar/Resgatar, comprar no
cartão, pagar fatura)

Em vez de escrever lógica nova, reutilizei funções do banco que **já
existem em produção** e já são usadas pela fila offline e pelo assistente de
IA do app mobile:

- `public.execute_offline_financial_action` (ações `move_goal` e
  `create_card_purchase`) — atômica, com trava de linha, idempotente.
- `public.finance_pay_invoice` — a mesma RPC que o app mobile já usa para
  pagar fatura "online".

Nenhuma migração nova foi criada — zero risco de schema. Testei as duas sem
autenticação (via `curl`) e confirmei que recusam com HTTP 401, como
esperado.
